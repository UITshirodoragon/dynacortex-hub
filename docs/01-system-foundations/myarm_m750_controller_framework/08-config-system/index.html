08. Hệ thống config

08.0. Mục tiêu

Hệ thống config của myarm_m750_controller_framework có mục tiêu tách cấu hình khỏi code, chuẩn hóa từng use case vận hành, đồng thời vẫn giữ khả năng cấu hình nhỏ theo từng tầng, từng adapter và từng profile phần cứng.

Dự án không dùng một file YAML khổng lồ cho toàn bộ hệ thống. Thay vào đó, dự án dùng mô hình:

Use Case Manifest
  -> chọn các micro config theo tầng
  -> chọn adapter/profile/variant
  -> merge thành resolved config
  -> validate trước khi chạy robot

Trong mô hình này:

  • Use case là điểm vào của runtime, benchmark hoặc debug.
  • Micro config là config nhỏ cho từng tầng, từng adapter hoặc từng chính sách safety.
  • Variant là phiên bản cụ thể của một micro config, ví dụ conservative, low_rate, serial, rviz_gui, fake_joint.
  • Resolved config là file config cuối cùng sau khi merge, dùng để chạy thực tế hoặc lưu lại trong artifact benchmark.

Nguyên tắc quan trọng nhất:

Code không tự quyết định runtime behavior. Code chỉ đọc config đã validate.

08.1. Nguyên tắc thiết kế

Config phải nằm ngoài code. Code không hard-code safety limit, workspace limit, benchmark count, device id, serial port, ROS topic, path log, camera role hoặc GUI mode.

Các giá trị vật lý phải có đơn vị rõ ràng trong tên field:

timeout_s
rate_hz
position_m
position_mm
angle_rad
angle_deg
velocity_rad_s
acceleration_rad_s2

Không dùng tên mơ hồ như:

timeout
rate
speed
position
angle
limit

Hệ thống config phải đảm bảo các yêu cầu sau:

  1. An toàn: robot thật chỉ được enable sau khi config đã validate joint limit, workspace limit, command rate và safe-fail policy.
  2. Tái lập: mọi lần benchmark hoặc hardware run phải lưu lại resolved_config.yaml.
  3. Dễ đọc: use case manifest phải cho biết rõ dùng path nào, adapter nào, runtime nào, input nào.
  4. Dễ mở rộng: thêm use case mới bằng cách compose config có sẵn, không copy nguyên một master YAML dài.
  5. Không trộn trách nhiệm: config của adapter không chứa logic application; config của use case không chứa toàn bộ chi tiết adapter.
  6. Local override không commit: các thông tin phụ thuộc máy cá nhân như serial port thật, IP máy, camera index, path local phải nằm trong config/local/.

08.2. Tầng config tổng quát

Dự án vẫn giữ phân lớp config theo kiến trúc:

Application
  -> Runtime
  -> Core SDK
  -> Ports
  -> Adapters
  -> Firmware/Hardware

Ý nghĩa từng tầng:

Application định nghĩa boundary của ứng dụng: có cho phép gọi raw firmware API không, có cho phép chạy baseline firmware coordinate không, use case nào thuộc production, diagnostic hoặc benchmark.

Runtime định nghĩa cách hệ thống chạy: native Python, ROS2, RViz2, WebSocket GUI, process supervisor, logging, replay hoặc benchmark runner.

Core SDK định nghĩa phần lõi dùng chung: frame convention, kinematics policy, controller policy, safety validation, trajectory sampling, workspace model.

Ports định nghĩa interface trừu tượng: hardware port, kinematics port, planner port, controller port, observation/debug port.

Adapters định nghĩa implementation cụ thể: real MyArmMControl adapter, fake hardware adapter, replay adapter, ROS2 adapter, RViz2 adapter, WebSocket adapter.

Firmware/Hardware định nghĩa thông tin gần hardware: serial transport, baudrate, firmware capability, camera device, robot profile, calibration.

08.4. Use case manifest

Use case manifest là file YAML nhỏ, dùng để chọn các config variant tương ứng với một kịch bản chạy cụ thể.

Use case manifest không nên chứa toàn bộ parameter chi tiết. Nó chỉ nên chứa:

  • id, name, safety level
  • runtime mode
  • hardware mode
  • danh sách config variant cần dùng
  • path package, launch, script, log, artifact
  • quality gate cần chạy
  • resolved config output

Ví dụ cấu trúc tổng quát:

schema_version: 1

use_case:
  id: ucxx_example
  name: Example use case
  safety_level: sim_only | hardware_manual | hardware_benchmark
  ros2: true
  simulation: false
  hardware: false

defaults:
  - application: boundary.default
  - runtime: ros2_foxy.rviz_gui
  - core_sdk/frames: default
  - core_sdk/kinematics: python_fk_ik
  - core_sdk/controller: external_joint_position
  - core_sdk/safety_joint_limits: conservative
  - core_sdk/safety_workspace: lab_table
  - core_sdk/safety_command_rate: low
  - core_sdk/safety_safe_fail: default
  - ports/hardware: default
  - ports/kinematics: default
  - ports/controller: default
  - adapters/hardware: fake_joint
  - adapters/input: websocket_gui
  - adapters/visualization: rviz_joint_state
  - firmware_hardware/robot: myarm_m750_default
  - profiles/machine: host_pc
  - profiles/network: localhost
  - debug_profiles/logging: default

overrides: {}

paths:
  packages: []
  entrypoints: {}
  launch: {}
  configs:
    resolved: config/_resolved/ucxx_example.resolved.yaml
  logs:
    output_dir: logs/use_cases/ucxx_example
  artifacts:
    output_dir: artifacts/use_cases/ucxx_example

quality_gates:
  required: []

08.8. Quy tắc default, variant và override

Mỗi config group có thể có nhiều variant. Không đặt tên kiểu default1, default2, custom2. Tên variant phải mô tả ý nghĩa kỹ thuật.

Ví dụ tốt:

safety.joint_limits_conservative.yaml
safety.command_rate_low.yaml
runtime.ros2_foxy.rviz_gui.yaml
hardware.fake_joint.yaml
hardware.myarm_mcontrol_real.yaml
kinematics.python_fk_ik.yaml

Ví dụ không nên dùng:

default1.yaml
default2.yaml
custom.yaml
test.yaml
new.yaml

Quy tắc chọn nơi đặt config:

Tình huống Cách quản lý
Cấu hình dùng lại bởi nhiều use case Tạo micro config variant
Cấu hình chỉ khác 1–3 giá trị trong một use case Dùng overrides trong use case

08.19. Config merge policy

Runtime final config được merge theo thứ tự:

1. application boundary
2. robot profile
3. machine profile
4. network profile
5. firmware/hardware config
6. core SDK config
7. port config
8. adapter config
9. runtime config
10. benchmark/debug profile
11. use-case overrides
12. local override

Kết quả merge tạo ra:

config/_resolved/<use_case_id>.resolved.yaml

Nếu là ROS2 use case, sinh thêm:

config/_resolved/<use_case_id>.ros2_params.yaml

Mọi config sau merge phải được validate trước khi robot được enable.

08.20. Local override

config/local/ dùng cho giá trị phụ thuộc máy cá nhân và không commit.

Ví dụ:

local:
  serial:
    port: /dev/ttyUSB0

  ros2:
    domain_id: 42

  websocket:
    port: 8765

  paths:
    lab_root: /home/jetson/lab

.gitignore trong config/local/:

*.yaml
*.yml
!.gitignore
!README.md

Không đưa secret, token, mật khẩu hoặc thông tin nhạy cảm vào config project.

08.21. Validation policy

Trước khi chạy hardware thật, hệ thống phải validate:

- use case id hợp lệ
- tất cả config path tồn tại
- không thiếu local override bắt buộc
- joint limit có min/max hợp lệ
- workspace limit có frame và unit rõ ràng
- command rate không vượt giới hạn use case
- hardware thật yêu cầu manual enable
- coordinate firmware chỉ được dùng trong use case được phép
- resolved_config.yaml đã được sinh

Nếu validation fail, robot không được enable.

08.22. Quy tắc chốt

Quy tắc vận hành config của dự án:

1. Use case manifest là điểm vào của runtime.
2. Micro config chia theo tầng và adapter.
3. Mỗi micro config có default và semantic variants.
4. Không dùng tên default1/default2/custom2.
5. Use case chỉ compose config, không chứa toàn bộ parameter chi tiết.
6. Config khác ít thì dùng overrides.
7. Config khác behavior thì tạo variant mới.
8. Hardware thật luôn cần safety config và manual enable.
9. Local override không commit.
10. Mỗi run quan trọng phải lưu resolved_config.yaml.

Mô hình này giúp dự án giữ được sự đơn giản khi mới phát triển, nhưng vẫn đủ chặt để mở rộng sang ROS2, RViz2, hardware thật, fake/replay, benchmark và các adapter khác trong tương lai.
